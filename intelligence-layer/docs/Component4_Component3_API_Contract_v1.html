POLICY DELIVERY CONTRACTVERSIONS & CONFIRMATION

Versioning and delivery

3Policy version rules

Component 4 sends baseVersion: the current policy reference used for calculation. Component 3 returns policyVersion: a new version after confirmed application.

Currentv1→ recommendation uses v1 → apply →v2

Maintain versions consistently per target. The next recommendation uses the confirmed version. Initial deadline references may be prometheus-config:1000; verify that startup configuration instead of assuming every first version is v1.

The URL segment /api/v1/ versions the API contract. It is unrelated to applied policy version strings.

4Acceptance response from Component 3

After validation, return HTTP 202 with:

{"status": "ACCEPTED"}

Component 4 records SENT. Acceptance does not mean the sidecars have applied the policy.

5Confirm application to Component 4

After the intended sidecars confirm application, Component 3 calls:

POST http://<COMPONENT4_HOST>:8090/api/v2/intelligence/changes/{proposalId}/acknowledge
Content-Type: application/json
X-RRPE-Control-Token: <Component4-control-token>
{
  "status": "APPLIED",
  "policyVersion": "v2",
  "appliedValue": 1440
}

Use the original proposal ID. The value must exactly match proposedValue; the version must be non-empty and different from baseVersion. The callback returns HTTP 204 on success. Its control token is required independently of optional receiver bearer authentication.

If application is already confirmed immediately, Component 3 may return the APPLIED JSON directly to the original POST. Confirm promptly while the proposal and current reference remain valid.

6Receiver checks

  • Deduplicate by proposal ID; validate action, target, units, decision and expiry.
  • Check current value and base version before applying. Reject stale updates.
  • Reject MOCK messages. Return non-2xx for invalid data or conflicts, such as 400 or 409.
  • Do not report APPLIED for partial sidecar application.
